01Vue d’ensemble : les trois couches

Le portail repose sur trois couches nettement séparées. Comprendre où vit chaque chose évite 90 % des erreurs de maintenance.

1. Frontend (pages statiques, servies par GitHub Pages depuis docs/ et la racine)
  ├─ admin.html — ton poste de pilotage (PC) : planning quotidien, wizards, équité
  ├─ dashboard.html — le portail perso du MAR : c'est le seul carrefour, toutes les pages ci-dessous s'ouvrent depuis ses tuiles
  ├─ index.html — le planning de l'équipe : planning, équité, année
  ├─ indispos.html — saisie des indisponibilités (tuile visible pendant la campagne seulement)
  ├─ absences.html — « Consultations à venir » : le contrôle d'absence au moment de la consultation. Deux portes — tuile MAR (restreinte pour l'instant) et session secrétariat par code partagé. Voir §19
  ├─ staff.html — outil du staff vacances (comité)
  ├─ crh.html et cr-anesthesie/ — générateurs de comptes rendus (réa et anesthésie)
  ├─ docs/module-liberal/maquette_estimateur_liberal.html — le module libéral (cotation, devis, déclaration). Malgré son nom et son emplacement, c'est un outil de production
  └─ docs/*.html — guides & présentations

2. Backend (Google Apps Script, déployé en Web App)
  └─ 5 fichiers .gs exposant une API doGet/doPost — voir §03

3. Données
  ├─ Google Sheets — la base : MEDECINS, INDISPOS_YYYY, GARDES_YYYY, STATS_GARDES_YYYY, PERIODES_VAC, GROUPES_VAC, PLANNING_OVERRIDES, CONFIG…
  └─ Drive privé « Planning-CHPG-JSON » — les JSON publiés (planning_YYYY.json, affectations_YYYY.json)
Le flux, en une phrase

Le frontend (admin ou MAR) appelle l’API Web App ; celle-ci lit/écrit dans Google Sheets ; à la publication, le planning est figé en JSON sur Drive privé, que le portail MAR relit pour l’affichage. Le code lui-même vit dans le dépôt GitHub, recopié dans l’éditeur Apps Script pour le backend.

04Le stockage : Google Sheets + Drive privé

Toute la donnée vivante est dans le Google Sheet lié — 25 onglets, des paramètres qu'on remplit à la main jusqu'aux grilles annuelles produites par les wizards.

Le classeur a son propre guide

Le détail onglet par onglet — colonnes, qui écrit, qui lit, ce qu'on peut modifier et ce qui casse si on se trompe — vit dans guide-fichier-maitre.html. Il n'est pas repris ici : deux inventaires finiraient par se contredire.

Les quatre repères à garder en tête depuis cette page : MEDECINS (l'effectif et les particularités), INDISPOS_{Y} (l'entrée de l'algorithme), GARDES_{Y} (sa sortie, et le verrou anti-régénération), STATS_GARDES_{Y} (la preuve d'équité, et la dette de l'année suivante).

Public vs privé — la ligne de partage

Le dépôt GitHub est public (Pages gratuit l'exige) : n'importe qui connaissant l'adresse peut lire son contenu — code, guides, et les noms de l'équipe (déjà publics par l'annuaire du CHPG). En revanche, aucune donnée nominative sensible n'y est committée : les JSON de planning (planning_YYYY.json, affectations_YYYY.json) et les archives de clôture (archives_stats/indispos_YYYY.json) vivent uniquement dans le dossier Drive non partagé « Planning-CHPG-JSON », lus/écrits via savePlanningToDrive / readPlanningFromDrive. Un échec d'écriture Drive fait échouer la publication (volontaire : pas de planning à moitié publié). Voir §16 pour le modèle complet.

05L’API Web App : requête → réponse

Le frontend ne touche jamais le Sheet directement : il passe par des appels HTTP à la Web App, chacun portant une action. Le routeur s'appelle _routeRequete_ (dans Indispos.gs) ; doGet/doPost ne font plus que l'appeler et le chronométrer. Il lit action, vérifie le rôle (user.role === 'admin' pour les actions sensibles), exécute, et renvoie du JSON.

Familles d’actions

  • Lecture : getMedecins, getGardes, getStats, getStatsLive, getVacValidation, getAllIndispos, getConflitsAll, getJoursFeries, getPlanningJson…
  • Écriture planning/équipe : saveMedecin, saveIndispos, savePeriodes, saveGroupes, savePlanningOverride, setDailyStatus, saveAffectations…
  • Cycle annuel : initYear, setActiveYear, generateGardes, publishPlanning, archiveYear.
  • Communication : sendCodes, sendCodesMar, envoyerRecapIndispos.
  • Module libéral : declareLiberal, deleteLiberal (écritures), listLiberal (le MAR connecté), listLiberalJour (admin, alimente le volet comité), getSecteurs, getSpecialites, getCotationsType.
    Lot 2A (27/07/2026) — LIBERAL_{Y} est passé de 6 à 9 colonnes (+ SPECIALITE, BR_CCAM, BR_NGAP) et la fusion jour+secteur a été supprimée : une ligne = un patient. Onglet SPECIALITES (12 codes) amorcé à la demande. L'élargissement de l'en-tête d'un onglet déjà rempli est idempotent et ne réécrit aucune ligne. Une spécialité vide est tolérée (compatibilité), une spécialité inconnue est refusée.
    Cotations types (27/07/2026) — onglet COTATIONS_TYPE : GROUPE | NOM | ORDRE | CODE | ROLE | MOD7 | MODA | LC. Aucun tarif n'y est stocké (il vient de ccam_actes.json à partir du code). La page n'affiche que les cotations types du groupe choisi, et rien tant qu'aucun groupe ne l'est. La migration de l'onglet (ajout de GROUPE en tête) est idempotente.
    Miroir maternité — définition UNIQUE (27/07/2026). Mardi et jeudi matin, le MAR placé en MAT fait aussi la CS-MAT : même personne. La règle n'existe pas dans les données, elle est recalculée à chaque usage. Elle avait été réécrite en dur dans l'affichage et dans le compteur d'équité, et oubliée dans l'export Excel — les consultations de maternité étaient visibles à l'écran et absentes du fichier du vendredi. Elle vit désormais dans MIROIR_MATER + estMiroirMater(dateISO, half), en tête d'admin.html, et les trois usages l'appellent. Dans l'export, elle s'applique après les overrides, sinon un placement manuel du comité serait écrasé.
    ⚠️ Ne jamais recopier la condition jsDow===2 || jsDow===4 ailleurs. Dette restante assumée : une seconde implémentation vit côté serveur dans Indispos.gs (getConsultAbsences) — fichiers différents, donc non fusionnables. Si la maternité change de jours, il y a DEUX endroits à modifier.
    Lot 2B (27/07/2026) — onglet LIBERAL_CA_{Y} (MOIS | MAR_ID | T_CCAM | PCT_CCAM | EXC_CCAM | T_NGAP | PCT_NGAP | EXC_NGAP) et action getReleveLiberal. ⚠️ LECTURE SEULE : le code n'écrit jamais dans cet onglet — le relevé est recopié à la main, rien ne passe par admin.html. Créé pré-rempli par creerReleveLiberalAnneeEnCours() (à lancer depuis l'éditeur ; idempotente). Le checksum vit en formules dans les colonnes J à M. getReleveLiberal renvoie aussi les affectations restantes, limitées aux MAR du relevé — getAffectations reste réservée à l'admin.
    ⚠️ Formules posées par setValues() : noms ANGLAIS obligatoires (IF, ROUND). Même dans un classeur en français, SI/ARRONDI renvoient #NAME? — constaté le 27/07. TEXT est à proscrire en plus : son code de format attend une virgule décimale en français et un point en anglais.
    Tri par marge dans absences.html (27/07/2026) — la liste « qui peut prendre le patient » est classée par marge CCAM décroissante, calculée côté page depuis getReleveLiberal. ⚠️ Cloisonnement des deux rôles : la page n'appelle getReleveLiberal que si ROLE === 'mar', et le serveur le refuserait de toute façon à un code secrétariat (absent de SECRETARIAT_ACTIONS). Double protection — ne retirer ni l'une ni l'autre. Sans relevé chargé, le tri redevient neutre et la page fonctionne normalement.
    ⚠️ Piège de cache vécu le 27/07 : la page met ces listes en sessionStorage. Une colonne ajoutée à l'onglet reste invisible tant que la session n'est pas fermée — et Ctrl+Maj+R ne vide pas le sessionStorage. Les clés sont désormais versionnées (chpgCotTypeLib_v2) : incrémenter le suffixe à chaque changement de structure, sinon la migration passe inaperçue chez tous les utilisateurs déjà connectés.

06Le cycle annuel : W1 → W2 → W3

Une année de planning se pilote par trois assistants (« wizards »), à lancer dans l’ordre depuis l’accueil d’admin.html. Ils encadrent les opérations irréversibles pour éviter les fausses manœuvres.

W1Initialiser N+1
→
W2Générer les gardes N+1
→
W3Clôturer N

Chronologie réelle : à l’automne de l’année N, on prépare N+1 (W1 en octobre → staff vacances → indispos → W2 en novembre). W3 clôture l’année N une fois que N+1 est prête — un garde-fou empêche de clôturer N si N+1 n’est pas générée.

07W1 — Initialiser l’année N+1 (6 étapes)

Fonction openWizard (le wizard d’initialisation, à ne pas confondre avec openWizardGardes qui est W2). Il prépare tout le terrain de l’année suivante. Les six étapes :

#ÉtapeCe qui se passe / se contrôle
1ÉquipeRevue des MARs actifs, quotités, emails. Alerte si un MAR actif n’a pas d’email (il ne recevra pas son code). Sauvegarde des quotités (saveWizQuotites).
2Périodes vacancesSaisie des fenêtres de congés scolaires (Zone B) de N+1. Elles bornent les congés MARs et bloquent le placement des récupérations (R). collectPeriodes.
3Groupes A/B/CÉcran de contrôle, en lecture seule : il affiche l'ordre de priorité par période après rotation annuelle. La composition des groupes se modifie dans l'onglet Équipe, pas ici (collectGroupes est volontairement vide). L'étape 4 réenregistre les groupes tels qu'ils ont été lus.
4Initialisation GSheetCréation des onglets INDISPOS_{N+1} et AFFECTATIONS_{N+1} (launchWizInit → action initYear). Garde-fou si l’onglet existe déjà.
5Staff physiqueRappel de la réunion de pose des vacances : c’est là que les seuils de présence sont respectés à la source.
6Envoi des codesEnvoi des codes d’accès + du lien de saisie des indispos aux MARs (launchWizardSendCodes).
Point technique — la rotation A/B/C

L’offset (= N+1 − 2026) fait tourner l’ordre de priorité chaque année, pour qu’aucun groupe ne soit systématiquement servi en premier. Le rang qui en résulte est exactement celui que l’audit couverture de W2 réutilise pour désigner le MAR le moins prioritaire à qui demander de décaler ses vacances.

Le sens est « le dernier devient le premier », entre groupes comme à l’intérieur d’un groupe : ABC → CAB → BCA → ABC, et A1 A2 A3 → A3 A1 A2 → A2 A3 A1. En code : (3 − offset % 3) % 3, jamais offset % 3.

⚠️ Règle écrite à quatre endroits

Elle vit dans staff.html, admin.html et deux fois dans Indispos.gs (plus l’outil testNotifierConflits). Le serveur a tourné à gauche jusqu’au 30/07/2026, alors que les écrans tournaient à droite : les deux ordres ne coïncidaient qu’une année sur trois (décalage nul), et une année sur trois le MAR désigné en conflit n’était pas celui affiché au staff. Constaté en réel sur l’hiver 2027. Toute modification doit être répercutée partout.

08W2 — Générer les gardes (3 étapes)

Fonction openWizardGardes. C’est l’assistant le plus contrôlé : il vérifie la faisabilité avant de lancer l’algorithme, pour ne jamais générer un planning bancal.

Étape 0 — Indispos & contrôles pré-génération

Charge en parallèle (Promise.all) : indispos (getAllIndispos), conflits vacances (getConflitsAll), fériés N et N+1 (getJoursFeries), et validation des vacances (getVacValidation, qui porte les rangs de priorité). Puis il affiche, dans l’ordre :

  • Récapitulatif des indispos : bloque si un MAR n’a pas saisi.
  • Conflits vacances : bloque s’il reste des conflits de seuil non arbitrés.
  • Audit équité indispos & souhaits : pour chaque axe (samedi/VD/jeudi/férié), calcule la cible exacte et vérifie qu’un MAR ne s’est pas rendu indisponible au point de ne plus pouvoir porter sa part. Bloque avec un message d’action ciblé.
  • Couverture jour par jour : liste chaque jour à moins de 6 MARs disponibles (🔴 <4, 🟠 4-5), le nombre de libérations à obtenir, et — nouveauté — le MAR le moins prioritaire (rang vacances) à solliciter en premier. Informe, ne bloque pas.
  • Couverture par semaine : capacité vs requis, semaines tendues.

Étape 1 — Validation des vacances

Tableau des périodes avec statut agrégé (✅ validé / ⚠️ partiel / ❌ conflits), lu depuis getVacValidation.

Étape 2 — Lancement

Récapitulatif final (nombre de MARs inclus, éventuels sans indispos) puis bouton ⚡ Générer les gardes → launchWizardGardes → action generateGardes(N+1). La génération prend 30–60 s et publie le planning (écriture des JSON sur le Drive privé).

⚠️ Le lancement enchaîne TROIS actions, pas une : generateGardes → publishPlanning → envoyerRecapIndispos. La troisième envoie à chaque MAR le récapitulatif de ses gardes, automatiquement, sans confirmation supplémentaire. Le wizard affiche le compte des envois, des MARs sans email et des échecs. (Le nom envoyerRecapGardes n’existe que comme libellé de journal ; l’action s’appelle bien envoyerRecapIndispos.)

Verrous

W2 est désactivé si N+1 ≤ 2026 (2026 sanctuarisé, saisi à la main) ou si GARDES_{N+1} existe déjà (protection anti-régénération : régénérer écraserait la preuve d’équité figée). Pour forcer : supprimer manuellement l’onglet GARDES_{N+1} dans le Sheet.

09W3 — Clôturer l’année (2 étapes)

Fonction openWizardCloture. Archive proprement l’année écoulée.

#ÉtapeDétail
1VérificationContrôle que l’année suivante est prête. Garde-fou : impossible de clôturer N si N+1 n’existe pas — sinon on se retrouverait sans planning au 1er janvier. ⚠️ Deux critères différents : l’écran lit le planning publié (getPlanningJson), le serveur lit les onglets (INDISPOS_{N+1} + STATS_GARDES_{N+1}). Une génération réussie mais non publiée bloque donc l’écran, pas le serveur.
2ArchivageLance trois actions : archiveYear → setActiveYear(N+1) → clearIndisposYear (cette dernière ferme la campagne de saisie).
⚠️ L’archivage est destructif pour le classeur maître

La documentation a longtemps annoncé une « suppression d’onglets commentée, non destructive ». C’est faux : moveSheets vaut true par défaut. archiveYear fait, dans l’ordre :

  1. alimente HISTORIQUE depuis STATS_GARDES_{N} — idempotent (une année déjà présente n’est pas dupliquée). La colonne NOEL/AN est lue dans GARDES_{N} réel, échanges et dons inclus, pas dans le snapshot figé ;
  2. range les JSON nominatifs dans le dossier Drive privé ;
  3. copie puis SUPPRIME du classeur maître les 4 onglets GARDES_{N}, INDISPOS_{N}, AFFECTATIONS_{N}, STATS_GARDES_{N} vers le classeur d’archive ;
  4. purge PLANNING_OVERRIDES de toutes les lignes de l’année et des années antérieures (auto-nettoyant si une clôture a été manquée).

Rien n’est perdu — l’année reste consultable dans le classeur d’archive — mais elle quitte le classeur principal.

Succès partiel : corrigé le 30/07/2026

Le dispatcher décide du succès en cherchant une ligne commençant par ❌ dans le rapport. Les échecs de transfert étaient marqués ⚠️ : l’action renvoyait succès, le wizard basculait l’année active et fermait la campagne alors que les onglets étaient toujours dans le maître — et, l’année ayant basculé, réarchiver N devenait impossible depuis l’assistant. Désormais « classeur d’archive inaccessible » et « transfert échoué » sont des ❌ bloquants ; les ⚠️ restants (onglet absent, purge sans effet) sont affichés sous la coche verte au lieu d’être avalés.

Note sur les overrides

Ne pas confondre OVERRIDES (ancien registre, l’onglet n’existe plus dans le classeur — code mort, voir roadmap) et PLANNING_OVERRIDES (les vraies retouches du comité, purgées à l’archivage).

10L’algorithme de gardes, sous le capot

generateGardes(year) dans generateur_gardes.gs. Le pipeline interne, dans l’ordre d’exécution :

  1. Cibles — pour chaque MAR et chaque axe (total, samedi, jeudi, VD, VJF, férié) : règle de trois sur la quotité (pctGardes), ajustée par la dette lue dans STATS_GARDES_{year-1} (amortie 60 %, plafond ±2).
  2. Souhaits garantis (placeSouhait, profil souhait_plafond) : placés en premier, jours de semaine uniquement, jamais WE/férié, avec freeBudget comme plafond.
  3. Placement chronologique (assign) : jour après jour, on classe les candidats via scoreSelect — d’abord blocked (règles dures : pas 2 jours de suite, pas sur absence, pas jeudi→samedi, VDM interdit hors souhait), puis spacingPenalty (espacement, semaine chargée, VDM en dernier recours = +5000), puis l’équité de l’axe (ratio/ratioTotal). Les rôles G/G2 sont attribués par assignRoles. Le week-end est une unité ven+dim (scoreVD).
  4. Rééquilibrage (l’optimiseur) : micro-échanges qui réduisent les écarts pondérés (VD > sam > jeu > total), sans casser une règle dure ni toucher un souhait honoré ; canHold interdit de créer un VDM par transfert.
  5. Récupérations : une R par samedi, hors périodes de vacances scolaires.
  6. Écriture : GARDES_{year} + STATS_GARDES_{year} (colonne MEDECIN = id).
Repères de non-régression — banc d'essai 400 années (29/07/2026)

292 312 gardes simulées sur 400 années (2027-2046, 20 tirages SCEN=0 à 19) : 0 journée sans binôme, écart médian 1,20 garde, et plus de 3 gardes d'écart dans 3 années sur 400 seulement — toutes dans le creux démographique. Ces chiffres sont ta référence de non-régression : si une modif du générateur les dégrade, c’est un signal.

11La publication : Drive privé & rendu MAR

À la fin de generateGardes (ou via publishPlanning), le planning est sérialisé et écrit sur Drive :

generateGardes / publishPlanning
  └─ savePlanningToDrive(planning_{year}.json)  → dossier privé « Planning-CHPG-JSON »
  └─ savePlanningToDrive(affectations_{year}.json)

Portail MAR (index.html, dashboard.html)
  └─ lit ces JSON via l’API Drive (getPlanningJson) — pas via des URL GitHub brutes

Conséquence pratique : après une génération, le planning est visible côté MAR sans aucun push GitHub. À l’inverse, modifier un JSON à la main dans le dépôt n’a aucun effet — la source est le Drive.

Échec de publication = échec total (voulu)

Si l’écriture Drive de planning_{year}.json échoue, la publication lève une erreur et s’arrête. Choix délibéré : mieux vaut pas de planning qu’un planning partiellement publié.

16Sécurité & confidentialité (le modèle réel)

Cette section décrit ce qui est protégé, à quel niveau, et où sont les limites assumées. Principe directeur : tout ce qui est nominatif et sensible est verrouillé côté serveur ; ce qui est exposé publiquement ne contient rien qu'on ne trouve déjà ailleurs.

Les deux périmètres

PérimètreVisibilitéContenu
Dépôt GitHub + Pages🌐 Public (adresse = accès)Code HTML/JS/GAS, guides, cr-anesthesie/data.js (noms MAR & chirurgiens), présentations avec cibles nominatives. Aucune absence, coordonnée, ni donnée patient.
Google Sheet + Drive🔒 Privé (compte comité, 2FA)Le vrai référentiel : MEDECINS (codes, emails, DECT, quotités, flags de statut), INDISPOS, GARDES, STATS, JSON de planning, archives de clôture.

La bascule entre les deux est nette : le frontend public ne détient aucune donnée sensible en dur ; il ne les obtient qu'en appelant la Web App avec un code valide, et la réponse vient du Sheet privé. Un visiteur du dépôt voit le code de l'app, pas les données qu'elle manipule.

Authentification & contrôle d'accès

  • Code-gating d'office. doGet/doPost appellent checkCode(code) ; sans code valide → {success:false,error:'Code invalide'}. Toutes les actions sont derrière cette porte, à une seule exception : getActiveYear, qui ne renvoie qu'un numéro d'année et répond avant checkCode. getStatus et getStatsLive étaient autrefois ouvertes elles aussi ; elles ont été refermées (elles renvoyaient des stats nominatives sans code) et sont désormais post-checkCode.
  • Trois rôles. checkCode renvoie admin (code CONFIG ▸ ADMIN_CODE), mar (code personnel, col G de MEDECINS) ou secretariat (code partagé CONFIG ▸ SECRETARIAT_CODE, liste blanche de deux actions — voir §19). Les actions d'écriture globale et de cycle annuel refusent tout non-admin via _deny().
  • Cloisonnement MAR. Un MAR ne lit/écrit que son périmètre : getIndispos/saveIndispos forcent targetId = user.id (seul l'admin peut viser un autre doctorId). Impossible pour un MAR d'atteindre la saisie d'un collègue.
  • Code jamais renvoyé au client. getMedecins expose hasCode:true/false, pas le code lui-même ; saveMedecin traite un code vide comme « inchangé » (un code ne peut pas être effacé par accident depuis le navigateur).
  • Transport. HTTPS partout ; les login passent en POST (corps), plus jamais en URL — évite que le code se retrouve dans un historique ou un log de proxy.

Où sont les secrets

Aucun secret n'est committé dans le dépôt. Le token GitHub (GITHUB_TOKEN) et la clé API Anthropic (ANTHROPIC_TOKEN) vivent dans l'onglet CONFIG du Sheet privé, lus à la volée (getGithubToken, getAnthropicToken). Le code d'accès admin est dans CONFIG ▸ ADMIN_CODE — plus aucun code de secours en dur dans le code (si la ligne manque, le login admin échoue, c'est volontaire).

Règle absolue du dépôt public

Ne jamais committer de valeur réelle : ni token, ni code d'accès, ni donnée nominative sensible. Un secret poussé même une fois reste dans l'historique git et doit être considéré comme grillé (→ le régénérer/changer). Les fonctions de test ne contiennent que des placeholders.

Le CRH et le transfert vers Anthropic

Le générateur de CRH (crh.html → genererCRH_ dans portail.gs) est le seul point où du texte clinique quitte l'environnement Google, vers l'API Anthropic (hors UE). Garde-fous en place :

  • Accès nominatif restreint : CRH_ALLOWED (liste blanche d'IDs).
  • Confirmation obligatoire : le bouton reste grisé tant que la case « texte anonymisé » n'est pas cochée ; le serveur refuse sans confirmAnonyme:true.
  • Pré-filtre client : detecteIdentifiant() bloque l'envoi si le texte contient un signal clair (« né(e) le », date de naissance, IPP/NIP, n° dossier, civilité + NOM). Volontairement conservateur (zéro faux positif sur un texte clinique normal).
  • Garde côté modèle : le prompt système refuse de produire un CR si un identifiant subsiste.
  • Traçabilité sans contenu : logAction note « CRH généré par X — anonymisation confirmée » ; jamais le texte clinique.

Le brouillon local du second outil (cr-anesthesie) est purgé du localStorage après copie du CR (PC partagés du bloc). Point encore ouvert (§backlog audit) : évaluer une option zéro-rétention / hébergement UE pour le CRH — décision à porter avec le référent RGPD du CHPG.

Journalisation & rétention

  • CONNEXIONS : horodatage + nom + rôle à chaque login. Auto-purge au-delà de 2 000 lignes.
  • LOGS : événements techniques. Auto-purge au-delà de 500 lignes.
  • Aucun de ces journaux ne contient de motif d'absence ni de donnée patient.

Ce qui reste des limites assumées

  • Le dépôt public expose noms d'équipe et cibles de gardes nominatives — jugé acceptable (noms déjà publics), non corrigé par choix (pas de plan payant).
  • Les codes MAR sont stockés en clair dans MEDECINS (pas de hachage) : protégés par l'accès 2FA au Sheet, pas cryptographiquement. Entropie 32⁸ ≈ 10¹², le brute-force via l'API reste non pratique, mais l'admin doit rester un code fort (plus de secours en dur).
  • Le CRH repose sur une discipline d'anonymisation (filtres + confirmation), pas sur une impossibilité technique de coller un identifiant.

Le fichier docs/module-liberal/ccam_actes.json alimente la recherche d'acte et les tarifs de l'estimateur. Détection automatique de l'obsolescence, mise à jour manuelle.

Constaté le 27/07/2026 : le fichier portait des codes v83 mais des tarifs v80 (2025) — un an de retard, soit environ 3 € de moins par acte sur 78 % des tarifs. Symptôme : un devis qui diverge du décompte de quelques euros.

Où lire la version en service : une mention permanente et discrète, en petit gris sous le champ de recherche d'acte de la page de cotation — « tarifs CCAM v84 · 03/07/2026 ». C'est le premier endroit où regarder quand un montant paraît faux.

Alerte : la page de cotation compare meta.effet à la date du jour et affiche un bandeau au-dessus de la recherche d'acte à partir de 8 mois (orange) puis 14 mois (rouge). Seuils = une puis deux revalorisations manquées. Les tarifs sont revalorisés une à deux fois par an ; contrôle conseillé en janvier et juillet.

Deux endroits alertent, avec les mêmes seuils :

  • la page de cotation — bandeau au-dessus de la recherche d'acte ;
  • le 🔍 Diagnostic de l'onglet Maintenance — ligne « Index CCAM (tarifs) : CCAM v84, effet 03/07/2026 — 24 jours », reprise dans le rapport copiable. C'est le seul écran regardé systématiquement, d'où le doublon assumé.

⚠️ Les seuils (8 et 14 mois) existent donc à DEUX endroits dans le code : TARIFS_ALERTE_MOIS/TARIFS_PERIME_MOIS dans la page de cotation, CCAM_ALERTE_MOIS/CCAM_PERIME_MOIS dans admin.html. Fichiers différents, donc non mutualisables — si l'un change, changer l'autre, sinon les deux écrans se contrediront.

Le contrôle du Diagnostic est purement côté page : le fichier est servi par GitHub Pages, le serveur GAS ne le voit pas. Il ne télécharge pas le mégaoctet — requête Range: bytes=0-600, les métadonnées étant en tête du JSON. Réseau coupé, fichier absent ou date manquante : avertissement, jamais d'exception — une vérification annexe ne doit pas faire tomber le diagnostic complet.

Dans CS_TEMPLATE, une ligne : CS-VASC · CS Vasculaire · O · O · MAR_PM = 1 · toutes les autres demi-journées à 0 · XL_LABEL = « ␣VASCULAIRE » · XL_BG = D9E1F2.

Puis Ctrl+Maj+R : une case « à pourvoir » apparaît le mardi après-midi dans l'onglet Planning, le comité clique dessus pour placer quelqu'un, et une ligne VASCULAIRE sort dans l'Excel du vendredi. Avec 1 seul créneau, les deux cellules de la demi-journée fusionnent ; avec 2, deux cases distinctes sont à pourvoir chaque semaine (c'est le cas du lundi après-midi en viscéral et en endoscopie).

Ne pas oublier le lien vers le secteur

Dans l'onglet SECTEURS, renseigner la colonne CS du secteur concerné avec le nouveau code. Sans ce lien, le panneau de placement proposera les MAR dans l'ordre habituel au lieu de mettre en tête ceux qui sont affectés au secteur.

⚠️ Les mentions « / URO. » et « / OPHTALMO. » des libellés Excel sont des abus de langage : le bloc viscéral couvre viscéral et uro, le bloc ORL couvre ORL et ophtalmo. Il n'existe pas de code distinct pour ces spécialités.

Retirer un secteur ou une consultation

Passer ACTIF à N, plutôt que supprimer la ligne

Supprimer une ligne ne touche pas les affectations déjà saisies : elles gardent l'ancien code. À la publication, normalizeAffectation ne le reconnaît plus et le MAR bascule en VOLANT — rien n'est perdu (la donnée reste dans AFFECTATIONS_{Y}), mais il quitte son secteur, et le code disparaît du sélecteur : impossible de le rechoisir.

Marche à suivre : réaffecter d'abord les MAR concernés, republier, puis passer ACTIF à N. C'est le mécanisme prévu pour le déménagement : anciens secteurs à N, nouveaux ajoutés, aucune ligne effacée.

Le 🔍 Diagnostic signale en erreur toute affectation pointant vers un secteur inexistant, inactif ou sans AFF, en nommant les MAR concernés. Un code inconnu est aussi tracé dans LOGS à la publication.

Code d'accès : la casse est ignorée (27/07/2026)

checkCode compare désormais le code en majuscules des deux côtés, pour les MAR, l'admin et le secrétariat. Auparavant la comparaison était stricte : taper son code en minuscules donnait « Code incorrect », sans aucun indice.

Le piège était invisible : les champs de saisie portent autocapitalize="characters", qui corrige tout seul sur mobile mais pas sur ordinateur. Le même code était donc accepté sur téléphone et refusé sur PC — incompréhensible pour l'utilisateur, et impossible à diagnostiquer à distance.

Sans risque de collision : generateCode() n'émet que des majuscules (ABCDEFGHJKLMNPQRSTUVWXYZ23456789, sans I ni O) et resetCodeMar vérifie déjà l'unicité en majuscules. ⚠️ Un code saisi un jour à la main dans le classeur doit rester unique une fois mis en majuscules.

Ajouté au passage : un code vide est refusé avant toute comparaison. Sans ce garde-fou, il correspondait à la cellule vide d'un MAR sans code.

20La boîte de réception (Messages)

Bouton ✉ Messages dans la barre d'admin.html : il ouvre les messages reçus sur planningchpg@gmail.com, adresse à laquelle les MARs écrivent leurs demandes. Trois actions serveur, toutes réservées à l'admin : mailNonLus (compteur), mailListe (20 messages), mailMessage (corps d'un message).

Le script passe par le service avancé Gmail, pas par GmailApp — ce dernier imposerait une autorisation large. Ni iframe (Gmail refuse d'être affiché dans une page tierce), ni lien vers Gmail (la boîte appartient au compte propriétaire de tout le back-end).

Autorisation : gmail.modify

Ouvrir un message le marque lu, sans quoi le compteur ne bougerait jamais et n'aurait aucun sens pour le comité. D'où gmail.modify et non gmail.readonly. Cela reste plus étroit que l'accès initial : la suppression définitive n'est pas possible. Les six autorisations du projet sont déclarées dans gas/appsscript.json, désormais versionné.

Google ne retire jamais une autorisation déjà accordée

Déclarer un périmètre plus étroit dans le manifeste ne suffit pas : l'accord antérieur subsiste. Il faut révoquer explicitement (myaccount.google.com → Données et confidentialité → Applications tierces → Tout supprimer), relancer une fonction pour déclencher le consentement, puis redéployer. ⚠️ Le site est hors service entre la révocation et le redéploiement.

Deux barrières contre l'injection

Le serveur ne renvoie que du texte brut (parcours des parties MIME, text/plain seulement ; le HTML d'un message est converti en texte côté serveur et ne part jamais). Et le client pose le corps avec textContent, jamais innerHTML. Expéditeur, objet et aperçu passent par _escHtml.

Performance

Le contenu ne part qu'au clic ; le compteur de non-lus part après l'affichage de l'admin, en tâche de fond. Ne jamais le mettre dans getAdminBootstrap : il ajouterait environ une seconde à chaque ouverture pour une fonction consultée occasionnellement. Au clic, le tiroir s'ouvre immédiatement avec un indicateur — même durée, ressenti tout autre. Quotas : 20 000 opérations Gmail par jour, un usage lourd en consomme environ 12 %.

Piège : « Impossible de décoder la chaîne »

Gmail encode le corps en base64 URL-safe et sans remplissage ; Utilities.base64DecodeWebSafe échoue dessus — environ 2 messages sur 3. Il faut normaliser soi-même (-→+, _→/, puis compléter à un multiple de 4) avant base64Decode.

Répondre depuis l'admin n'est pas prévu, volontairement : ce serait une écriture, avec verrou et quota d'envoi. Décision distincte, à reprendre explicitement.

22Le « + » de case à pourvoir

C'est le signal le plus regardé de la grille, et il n'était documenté nulle part. Un « + » orange dans une case de bloc ne veut pas dire « il manque quelqu'un » : il veut dire « un habitué du secteur manque à l'appel aujourd'hui, et personne ne l'a remplacé ».

La règle générale

  1. Qui devrait être là ? Les MARs dont l'affectation du mois (AFFECTATIONS_{Y}) est ce secteur — les « réguliers ».
  2. Combien en manque-t-il ? Les réguliers absents ce jour (RG, congé, formation, récup, temps partiel…), plus ceux que le comité a déplacés ou retirés ailleurs ce demi-jour, moins les personnes présentes dans la case qui ne sont pas réguliers du secteur — celles-là comptent comme remplaçants.
  3. Le résultat est le nombre de « + ».
  4. Plancher : une case entièrement vide affiche toujours au moins un « + ».

Jamais le week-end ni les jours fériés. VOLANT, DVI et les consultations ne suivent pas cette règle.

Les quatre secteurs qui ont leur propre règle

SecteurRègle réellement codée
CIRègle générale, sauf le jeudi — ce jour-là c'est la radio interventionnelle seule.
RIRequis mercredi et jeudi matin uniquement. Jamais l'après-midi, jamais les autres jours, même vide.
MATToujours pourvue, matin et après-midi.
DVIRequis mardi matin uniquement (pose de DVI).

Les consultations, elles, sont pilotées par les données

Pour une consultation, le « + » vaut simplement effectif requis − présents, le requis étant lu dans les dix colonnes LUN_AM … VEN_PM de CS_TEMPLATE. Aucun code de consultation n'est écrit en dur.

La dette à connaître

Les secteurs de bloc, eux, sont encore décrits par cinq blocs de code avec leurs codes en dur dans admin.html. Au déménagement, quand les codes changeront, le « + » s'éteindra partout, en silence — sans erreur ni message. La cible retenue est de faire passer les secteurs sur le modèle des consultations : un tableau de chiffres dans l'onglet SECTEURS. Voir la roadmap, section NCHPG.

23Mesurer la performance : chrono() et chronoClics()

Deux commandes à taper dans la console du navigateur (F12 → Console), disponibles sur admin.html, index.html, dashboard.html, indispos.html et absences.html. Elles ne modifient rien : elles observent et impriment un tableau.

chrono() — le budget complet de la page

S'affiche automatiquement à la fin de l'ouverture d'admin.html. Sept parties : la page elle-même, les ressources chargées, les appels serveur, le détail interne du bootstrap, les étapes du chargement, le temps passé dans les fonctions d'affichage, et le temps pendant lequel l'écran est resté figé.

Chaque appel serveur se lit en trois temps, et les confondre mène à optimiser au mauvais endroit :

ColonneCe qu'elle mesure
avant doGetNotre code global, exécuté avant le point d'entrée : lecture du classeur par TEST_YEAR. Devrait valoir quelques millisecondes grâce au cache de configuration.
doGetLe travail utile. Sa ventilation figure dans la partie « détail du bootstrap ».
réseauTout le reste : plancher de la plateforme (~1,4 s), compilation de nos 545 Ko de .gs (~0,7 s), et la file d'attente Google — le terme qui décide des mauvais jours, mesuré entre 2,7 s et 18,2 s le 01/08 à trois minutes d'écart.

La partie « détail de getAdminBootstrap » ventile les dix opérations du bootstrap, triées de la plus coûteuse à la plus légère. C'est elle qui a montré que les lectures d'onglets sautent d'un facteur 10 d'une minute à l'autre là où les lectures Drive restent stables — origine du cache de configuration.

chronoClics() — le coût d'une interaction

Pour chaque clic de plus de 16 ms : la cible, puis trois temps qu'il ne faut pas confondre.

ColonneCe qu'elle mesureCe qu'on peut en faire
attenteDélai entre le clic et le début du traitement Le navigateur était occupé ailleurs — regarder « écran figé »
traitementTemps passé dans notre code Le seul temps qu'on puisse réduire nous-mêmes
écranPeinture après le traitement Trop d'éléments réaffichés d'un coup

Repère : au-delà de 200 ms un clic est ressenti comme lent, au-delà de 500 ms comme bloqué.

Chrome ou Edge uniquement

chronoClics() repose sur une mesure que Safari et Firefox ne fournissent pas : sur ces navigateurs la liste reste vide. Le reste de chrono() fonctionne partout.

Lire la colonne « dont écran figé »

Dans la partie Affichage, une fonction qui attend le serveur (par exemple initDashboard) affiche un cumul de plusieurs secondes mais un « écran figé » de quelques millisecondes : elle est lente sans être bloquante. Ne pas chercher à l'optimiser. À l'inverse, renderWeek affiche les deux temps identiques : tout ce qu'elle consomme est du blocage direct.

Trois faux coupables, écartés par la mesure du 01/08

Chacun paraissait évident à la lecture du code. Aucun n'était en cause : renderWeek(), rappelée en entier à chaque placement, coûte 17 ms ; les 500 Ko d'admin.html coûtent 0,44 s d'analyse, soit 2 % de l'ouverture ; le JSON.parse d'une réponse de 350 Ko coûte 6 ms. Le coût d'un clic est la peinture (100 à 230 ms), pas notre code (10 à 25 ms). Mesurer d'abord, conclure ensuite — et se méfier des raisonnements fondés sur la taille d'un fichier.

Ne jamais comparer deux mesures prises à des heures différentes

Apps Script n'offre aucune garantie de performance : le 28/07/2026 le même code est passé de 3,1 à 6,1 s côté serveur en trois heures. Un avant/après n'a de sens que si les deux mesures sont prises dans la même session, à quelques minutes d'intervalle.
