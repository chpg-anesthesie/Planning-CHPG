01Vue d’ensemble : les trois couches

Le portail repose sur trois couches nettement séparées. Comprendre où vit chaque chose évite 90 % des erreurs de maintenance.

1. Frontend (pages statiques, servies par GitHub Pages depuis docs/ et la racine)
  ├─ admin.html — ton poste de pilotage (PC) : planning quotidien, wizards, équité
  ├─ index.html — le portail des MARs : planning, équité, année
  ├─ indispos.html / staff.html / dashboard.html — saisie indispos, portail perso, accueil
  └─ docs/*.html — guides & présentations

2. Backend (Google Apps Script, déployé en Web App)
  └─ 4 fichiers .gs exposant une API doGet/doPost

3. Données
  ├─ Google Sheets — la base : MEDECINS, INDISPOS_YYYY, GARDES_YYYY, STATS_GARDES_YYYY, PERIODES_VAC, GROUPES_VAC, PLANNING_OVERRIDES, CONFIG…
  └─ Drive privé « Planning-CHPG-JSON » — les JSON publiés (planning_YYYY.json, affectations_YYYY.json)
Le flux, en une phrase

Le frontend (admin ou MAR) appelle l’API Web App ; celle-ci lit/écrit dans Google Sheets ; à la publication, le planning est figé en JSON sur Drive privé, que le portail MAR relit pour l’affichage. Le code lui-même vit dans le dépôt GitHub, recopié dans l’éditeur Apps Script pour le backend.

02Le dépôt GitHub, source de vérité

Règle cardinale : le dépôt chpg-anesthesie/Planning-CHPG (branche main) contient 100 % du code de production, frontend et backend. Toute modification faite ailleurs sans être committée est perdue.

Où trouver quoi

CheminContenu
/ (racine)Pages frontend : admin.html, index.html, staff.html, indispos.html, dashboard.html
/docsServi par GitHub Pages : guides, présentations, ce document
/docs/module-liberalLe chantier module libéral (estimateur, antisèche, conception)
/gasCopie du code Apps Script : code.gs, Indispos.gs, generateur_gardes.gs, setup_annee.gs, portail.gs
Frontend vs backend : deux circuits de livraison

Frontend (HTML/JS/docs) : le push GitHub suffit — GitHub Pages sert la nouvelle version, tu fais Ctrl+Maj+R pour vider le cache. Backend (fichiers .gs) : le push GitHub ne suffit pas — il faut recopier le fichier dans l’éditeur Apps Script, puis souvent redéployer la Web App (voir §13).

03Le backend Apps Script (les 5 fichiers .gs)

Le backend est un projet Apps Script lié au Google Sheet de production, déployé comme application Web. Cinq fichiers se partagent le travail :

FichierResponsabilité
Indispos.gsLe cœur de l’API : doGet/doPost et la totalité des actions (getMedecins, getVacValidation, generateGardes, initYear, archiveYear, publishPlanning, sendCodes…). C’est le plus gros fichier.
generateur_gardes.gsL’algorithme generateGardes(year) : cibles, placement, équité par axe, dette inter-annuelle, souhaits, VDM. Détaillé au §10.
code.gsPlacement des secteurs du bloc (generatePlanningFromGardes), gestion des overrides (PLANNING_OVERRIDES), getJoursFeries, pushFileToGitHub, onEdit, reconstruction 2026, buildStats2026.
setup_annee.gssetupAnnee (crée INDISPOS/AFFECTATIONS de N+1), archiveYear (archive stats/indispos).
portail.gsLogique du portail perso / dashboard (données agrégées par MAR).
Piège classique

Symptôme « Action inconnue » ou « fonction introuvable » après une recopie = le dépôt était incomplet, ou un fichier n’a pas été recopié. Le dépôt doit toujours refléter l’intégralité du code en service.

04Le stockage : Google Sheets + Drive privé

Toute la donnée vivante est dans le Google Sheet lié. Les onglets structurants :

OngletRôle
MEDECINSLe référentiel : id, nom, initiales, actif, quotité, %gardes, email, dect, dates début/fin, et les flags de statut (colonnes) : no_garde, only_18, no_weekend, rythme_2sur2, souhait_plafond (col P), tp_jours_fixes (col Q).
INDISPOS_YYYYGrille par MAR × jour : VAC, INDISPO, FORM, SOUHAIT… Base de l’algorithme.
GARDES_YYYYLe planning de gardes généré (G = réa, G2 = mater/bloc).
STATS_GARDES_YYYYLa preuve d’équité : cible et réel par axe, par MAR. Sert aussi de base à la dette de l’année N+1.
PERIODES_VAC / GROUPES_VACPériodes de vacances (dates, seuil de présence) et groupes de priorité A/B/C.
PLANNING_OVERRIDESRetouches manuelles du comité au planning quotidien, indexées par date.
CONFIGParamètres, dont le token GitHub côté serveur (getGithubToken).
Public vs privé — la ligne de partage

Le dépôt GitHub est public (Pages gratuit l'exige) : n'importe qui connaissant l'adresse peut lire son contenu — code, guides, et les noms de l'équipe (déjà publics par l'annuaire du CHPG). En revanche, aucune donnée nominative sensible n'y est committée : les JSON de planning (planning_YYYY.json, affectations_YYYY.json) et les archives de clôture (archives_stats/indispos_YYYY.json) vivent uniquement dans le dossier Drive non partagé « Planning-CHPG-JSON », lus/écrits via savePlanningToDrive / readPlanningFromDrive. Un échec d'écriture Drive fait échouer la publication (volontaire : pas de planning à moitié publié). Voir §16 pour le modèle complet.

05L’API Web App : requête → réponse

Le frontend ne touche jamais le Sheet directement : il passe par des appels HTTP à la Web App, chacun portant une action. Le routeur (doGet/doPost dans Indispos.gs) lit action, vérifie le rôle (user.role === 'admin' pour les actions sensibles), exécute, et renvoie du JSON.

Familles d’actions

  • Lecture : getMedecins, getGardes, getStats, getStatsLive, getVacValidation, getAllIndispos, getConflitsAll, getJoursFeries, getPlanningJson…
  • Écriture planning/équipe : saveMedecin, saveIndispos, savePeriodes, saveGroupes, savePlanningOverride, setDailyStatus, saveAffectations…
  • Cycle annuel : initYear, setActiveYear, generateGardes, publishPlanning, archiveYear, validerSemaine.
  • Communication : sendCodes, sendCodesMar, envoyerRecapIndispos.
Authentification

À la connexion, login renvoie un rôle. L’admin (toi/le comité) a accès à tout ; un MAR n’a que la lecture de son périmètre et la saisie de ses indispos. Les actions de génération/archivage sont refusées (_deny()) hors admin.

06Le cycle annuel : W1 → W2 → W3

Une année de planning se pilote par trois assistants (« wizards »), à lancer dans l’ordre depuis l’accueil d’admin.html. Ils encadrent les opérations irréversibles pour éviter les fausses manœuvres.

W1Initialiser N+1
→
W2Générer les gardes N+1
→
W3Clôturer N

Chronologie réelle : à l’automne de l’année N, on prépare N+1 (W1 en octobre → staff vacances → indispos → W2 en novembre). W3 clôture l’année N une fois que N+1 est prête — un garde-fou empêche de clôturer N si N+1 n’est pas générée.

↑ Sommaire

07W1 — Initialiser l’année N+1 (6 étapes)

Fonction openWizard (le wizard d’initialisation, à ne pas confondre avec openWizardGardes qui est W2). Il prépare tout le terrain de l’année suivante. Les six étapes :

#ÉtapeCe qui se passe / se contrôle
1ÉquipeRevue des MARs actifs, quotités, emails. Alerte si un MAR actif n’a pas d’email (il ne recevra pas son code). Sauvegarde des quotités (saveWizQuotites).
2Périodes vacancesSaisie des fenêtres de congés scolaires (Zone B) de N+1. Elles bornent les congés MARs et bloquent le placement des récupérations (R). collectPeriodes.
3Groupes A/B/COrdre de priorité par période avec rotation annuelle. La base ORDRE_BASE (ex. HIVER:CAB, ETE:ABC) subit un décalage offset = (N+1 − 2026) % 3. collectGroupes.
4Initialisation GSheetCréation des onglets INDISPOS_{N+1} et AFFECTATIONS_{N+1} (launchWizInit → action initYear). Garde-fou si l’onglet existe déjà.
5Staff physiqueRappel de la réunion de pose des vacances : c’est là que les seuils de présence sont respectés à la source.
6Envoi des codesEnvoi des codes d’accès + du lien de saisie des indispos aux MARs (launchWizardSendCodes).
Point technique — la rotation A/B/C

L’offset fait tourner l’ordre de priorité chaque année, pour qu’aucun groupe ne soit systématiquement servi en premier. Le rang qui en résulte est exactement celui que l’audit couverture de W2 réutilise pour désigner le MAR le moins prioritaire à qui demander de décaler ses vacances.

08W2 — Générer les gardes (3 étapes)

Fonction openWizardGardes. C’est l’assistant le plus contrôlé : il vérifie la faisabilité avant de lancer l’algorithme, pour ne jamais générer un planning bancal.

Étape 0 — Indispos & contrôles pré-génération

Charge en parallèle (Promise.all) : indispos (getAllIndispos), conflits vacances (getConflitsAll), fériés N et N+1 (getJoursFeries), et validation des vacances (getVacValidation, qui porte les rangs de priorité). Puis il affiche, dans l’ordre :

  • Récapitulatif des indispos : bloque si un MAR n’a pas saisi.
  • Conflits vacances : bloque s’il reste des conflits de seuil non arbitrés.
  • Audit équité indispos & souhaits : pour chaque axe (samedi/VD/jeudi/férié), calcule la cible exacte et vérifie qu’un MAR ne s’est pas rendu indisponible au point de ne plus pouvoir porter sa part. Bloque avec un message d’action ciblé.
  • Couverture jour par jour : liste chaque jour à moins de 6 MARs disponibles (🔴 <4, 🟠 4-5), le nombre de libérations à obtenir, et — nouveauté — le MAR le moins prioritaire (rang vacances) à solliciter en premier. Informe, ne bloque pas.
  • Couverture par semaine : capacité vs requis, semaines tendues.

Étape 1 — Validation des vacances

Tableau des périodes avec statut agrégé (✅ validé / ⚠️ partiel / ❌ conflits), lu depuis getVacValidation.

Étape 2 — Lancement

Récapitulatif final (nombre de MARs inclus, éventuels sans indispos) puis bouton ⚡ Générer les gardes → launchWizardGardes → action generateGardes(N+1). La génération prend 30–60 s, publie le planning et notifie les MARs.

Verrous

W2 est désactivé si N+1 ≤ 2026 (2026 sanctuarisé, saisi à la main) ou si GARDES_{N+1} existe déjà (protection anti-régénération : régénérer écraserait la preuve d’équité figée). Pour forcer : supprimer manuellement l’onglet GARDES_{N+1} dans le Sheet.

09W3 — Clôturer l’année (2 étapes)

Fonction openWizardCloture. Archive proprement l’année écoulée.

#ÉtapeDétail
1VérificationContrôle que l’année suivante est prête (W1 + W2 faits). Garde-fou : impossible de clôturer N si N+1 n’existe pas — sinon on se retrouverait sans planning au 1er janvier.
2ArchivageRécapitule l’équité finale et archive (archiveYear) : push des stats/indispos vers l’archive. Suppression d’onglets commentée (non destructif par sécurité).
Note sur les overrides

setActiveYear archive/vide l’onglet OVERRIDES (hérité, ancien système) mais ne touche pas à PLANNING_OVERRIDES (les vraies retouches comité). Ne pas confondre les deux.

10L’algorithme de gardes, sous le capot

generateGardes(year) dans generateur_gardes.gs. Le pipeline interne, dans l’ordre d’exécution :

  1. Cibles — pour chaque MAR et chaque axe (total, samedi, jeudi, VD, VJF, férié) : règle de trois sur la quotité (pctGardes), ajustée par la dette lue dans STATS_GARDES_{year-1} (amortie 60 %, plafond ±2).
  2. Souhaits garantis (placeSouhait, profil souhait_plafond) : placés en premier, jours de semaine uniquement, jamais WE/férié, avec freeBudget comme plafond.
  3. Placement chronologique (assign) : jour après jour, on classe les candidats via scoreSelect — d’abord blocked (règles dures : pas 2 jours de suite, pas sur absence, pas jeudi→samedi, VDM interdit hors souhait), puis spacingPenalty (espacement, semaine chargée, VDM en dernier recours = +5000), puis l’équité de l’axe (ratio/ratioTotal). Les rôles G/G2 sont attribués par assignRoles. Le week-end est une unité ven+dim (scoreVD).
  4. Rééquilibrage (l’optimiseur) : micro-échanges qui réduisent les écarts pondérés (VD > sam > jeu > total), sans casser une règle dure ni toucher un souhait honoré ; canHold interdit de créer un VDM par transfert.
  5. Récupérations : une R par samedi, hors périodes de vacances scolaires.
  6. Écriture : GARDES_{year} + STATS_GARDES_{year} (colonne MEDECIN = id).
Repères validés en simulation (20 ans)

0 violation de règle dure sur 14 580 gardes, installés entre 98,7 % et 102,2 % de leur juste part, écart individuel annuel 1–2 gardes (pire 2,7). Ces chiffres sont ta référence de non-régression : si une modif du générateur les dégrade, c’est un signal.

11La publication : Drive privé & rendu MAR

À la fin de generateGardes (ou via publishPlanning), le planning est sérialisé et écrit sur Drive :

generateGardes / publishPlanning
  └─ savePlanningToDrive(planning_{year}.json)  → dossier privé « Planning-CHPG-JSON »
  └─ savePlanningToDrive(affectations_{year}.json)

Portail MAR (index.html, dashboard.html)
  └─ lit ces JSON via l’API Drive (getPlanningJson) — pas via des URL GitHub brutes

Conséquence pratique : après une génération, le planning est visible côté MAR sans aucun push GitHub. À l’inverse, modifier un JSON à la main dans le dépôt n’a aucun effet — la source est le Drive.

Échec de publication = échec total (voulu)

Si l’écriture Drive de planning_{year}.json échoue, la publication lève une erreur et s’arrête. Choix délibéré : mieux vaut pas de planning qu’un planning partiellement publié.

13Le pipeline de déploiement du code

Frontend (HTML / JS / docs)

1Push GitHub (API Contents)
→
2GitHub Pages sert la version
→
3Ctrl+Maj+R

Immédiat. La règle d’or côté push : GET du SHA du fichier juste avant le PUT (plusieurs conversations écrivent sur le même dépôt), node --check sur tout JS, vérification de l’équilibre des balises.

Backend (fichiers .gs)

1Push GitHub (copie du dépôt)
→
2Recopie manuelle dans l’éditeur Apps Script
→
3Nouveau déploiement Web App
→
4Hard-refresh

Le push GitHub ne fait que documenter/sauvegarder le code backend. Pour qu’il s’exécute, il faut le coller dans l’éditeur Apps Script, puis redéployer la Web App comme nouvelle version (sinon l’ancienne reste servie). Certains changements ne servant qu’à la génération (comme generateur_gardes.gs) n’exigent pas de redéploiement Web App, juste la recopie avant la prochaine génération.

La règle qui sauve

Ne jamais modifier un .gs directement dans l’éditeur sans committer aussitôt dans le dépôt : à la prochaine recopie dépôt → éditeur, ta modif non commitée serait écrasée.

14Dépannage & pièges connus

SymptômeCause probable / action
« Action inconnue » / « fonction introuvable »Dépôt/éditeur incomplet ou fichier non recopié. Vérifier que les 5 .gs sont à jour dans l’éditeur, redéployer.
Une modif backend n’a aucun effetWeb App pas redéployée (nouvelle version), ou modif faite dans l’éditeur puis écrasée par une recopie du dépôt.
Le planning MAR ne se met pas à jourC’est le Drive qui fait foi, pas GitHub. Vérifier que la publication (écriture Drive) a réussi ; côté MAR, Ctrl+Maj+R.
Un profil « souhait garanti » (Prunet) sort en rouge au certificatLe flag souhait_plafond (col P de MEDECINS) n’est pas coché : le code ne peut pas le reconnaître et l’exclure.
W2 refuse de générerN+1 ≤ 2026 (sanctuarisé) ou GARDES_{N+1} déjà présent. Voir les verrous du §8.
Trou de couverture à la générationTrop d’absences simultanées non détectées. L’audit de W2 (§8) les signale avant ; suivre la suggestion du MAR le moins prioritaire.
Modif du générateur qui dégrade l’équitéComparer aux repères de non-régression du §10 (98,7–102,2 %, 0 violation). Le banc d’essai 20 ans est l’outil de contrôle.

Santé du classeur

⚠️ Onglet LOGS/CONNEXIONS volumineux (> 20 000 lignes)Supprimer les lignes anciennes (garder les en-têtes).

16Sécurité & confidentialité (le modèle réel)

Cette section décrit ce qui est protégé, à quel niveau, et où sont les limites assumées. Principe directeur : tout ce qui est nominatif et sensible est verrouillé côté serveur ; ce qui est exposé publiquement ne contient rien qu'on ne trouve déjà ailleurs.

Les deux périmètres

PérimètreVisibilitéContenu
Dépôt GitHub + Pages🌐 Public (adresse = accès)Code HTML/JS/GAS, guides, cr-anesthesie/data.js (noms MAR & chirurgiens), présentations avec cibles nominatives. Aucune absence, coordonnée, ni donnée patient.
Google Sheet + Drive🔒 Privé (compte comité, 2FA)Le vrai référentiel : MEDECINS (codes, emails, DECT, quotités, flags de statut), INDISPOS, GARDES, STATS, JSON de planning, archives de clôture.

La bascule entre les deux est nette : le frontend public ne détient aucune donnée sensible en dur ; il ne les obtient qu'en appelant la Web App avec un code valide, et la réponse vient du Sheet privé. Un visiteur du dépôt voit le code de l'app, pas les données qu'elle manipule.

Authentification & contrôle d'accès

  • Code-gating d'office. doGet/doPost appellent checkCode(code) ; sans code valide → {success:false,error:'Code invalide'}. Toutes les actions sont derrière cette porte, à trois exceptions volontairement ouvertes car non sensibles : getActiveYear (un numéro d'année), getStatus et getStatsLive — ces deux dernières ont été refermées (elles renvoyaient des stats nominatives sans code) et sont désormais post-checkCode.
  • Deux rôles. checkCode renvoie admin (code CONFIG ▸ ADMIN_CODE) ou mar (code personnel, col G de MEDECINS). Les actions d'écriture globale et de cycle annuel refusent tout non-admin via _deny().
  • Cloisonnement MAR. Un MAR ne lit/écrit que son périmètre : getIndispos/saveIndispos forcent targetId = user.id (seul l'admin peut viser un autre doctorId). Impossible pour un MAR d'atteindre la saisie d'un collègue.
  • Code jamais renvoyé au client. getMedecins expose hasCode:true/false, pas le code lui-même ; saveMedecin traite un code vide comme « inchangé » (un code ne peut pas être effacé par accident depuis le navigateur).
  • Transport. HTTPS partout ; les login passent en POST (corps), plus jamais en URL — évite que le code se retrouve dans un historique ou un log de proxy.

Où sont les secrets

Aucun secret n'est committé dans le dépôt. Le token GitHub (GITHUB_TOKEN) et la clé API Anthropic (ANTHROPIC_TOKEN) vivent dans l'onglet CONFIG du Sheet privé, lus à la volée (getGithubToken, getAnthropicToken). Le code d'accès admin est dans CONFIG ▸ ADMIN_CODE — plus aucun code de secours en dur dans le code (si la ligne manque, le login admin échoue, c'est volontaire).

Règle absolue du dépôt public

Ne jamais committer de valeur réelle : ni token, ni code d'accès, ni donnée nominative sensible. Un secret poussé même une fois reste dans l'historique git et doit être considéré comme grillé (→ le régénérer/changer). Les fonctions de test ne contiennent que des placeholders.

Le CRH et le transfert vers Anthropic

Le générateur de CRH (crh.html → genererCRH_ dans portail.gs) est le seul point où du texte clinique quitte l'environnement Google, vers l'API Anthropic (hors UE). Garde-fous en place :

  • Accès nominatif restreint : CRH_ALLOWED (liste blanche d'IDs).
  • Confirmation obligatoire : le bouton reste grisé tant que la case « texte anonymisé » n'est pas cochée ; le serveur refuse sans confirmAnonyme:true.
  • Pré-filtre client : detecteIdentifiant() bloque l'envoi si le texte contient un signal clair (« né(e) le », date de naissance, IPP/NIP, n° dossier, civilité + NOM). Volontairement conservateur (zéro faux positif sur un texte clinique normal).
  • Garde côté modèle : le prompt système refuse de produire un CR si un identifiant subsiste.
  • Traçabilité sans contenu : logAction note « CRH généré par X — anonymisation confirmée » ; jamais le texte clinique.

Le brouillon local du second outil (cr-anesthesie) est purgé du localStorage après copie du CR (PC partagés du bloc). Point encore ouvert (§backlog audit) : évaluer une option zéro-rétention / hébergement UE pour le CRH — décision à porter avec le référent RGPD du CHPG.

Journalisation & rétention

  • CONNEXIONS : horodatage + nom + rôle à chaque login. Auto-purge au-delà de 2 000 lignes.
  • LOGS : événements techniques. Auto-purge au-delà de 500 lignes.
  • Aucun de ces journaux ne contient de motif d'absence ni de donnée patient.

Ce qui reste des limites assumées

  • Le dépôt public expose noms d'équipe et cibles de gardes nominatives — jugé acceptable (noms déjà publics), non corrigé par choix (pas de plan payant).
  • Les codes MAR sont stockés en clair dans MEDECINS (pas de hachage) : protégés par l'accès 2FA au Sheet, pas cryptographiquement. Entropie 32⁸ ≈ 10¹², le brute-force via l'API reste non pratique, mais l'admin doit rester un code fort (plus de secours en dur).
  • Le CRH repose sur une discipline d'anonymisation (filtres + confirmation), pas sur une impossibilité technique de coller un identifiant.
